⚠️ SANDBOX MODE

This gateway is currently in test/sandbox mode. No real payments are processed. For production, integration with an acquiring bank is required.

How the Sandbox Works

Test the full payment flow with mock card processing. No real money moves.

  1. 1 Register Merchant Create a merchant account and receive API keys (sk_test_/sk_live_).
  2. 2 Create Order POST to /v1/orders with amount, currency (GYD), and description.
  3. 3 Hosted Checkout Redirect customer to the secure checkout URL. Card data entered only here.
  4. 4 Mock Processor Test cards are processed in-memory. Only documented test cards are accepted.
  5. 5 Webhook Notification Signed webhook sent to your endpoint with payment result.

Authentication

All API requests require authentication with your merchant API key.

API Keys

You receive two API keys when you create a merchant account:

  • sk_test_... — Test mode key (sandbox transactions)
  • sk_live_... — Live mode key (real transactions, when enabled)

Authentication Header

Authorization: Bearer sk_test_abc123def456...

Example Request

curl -X POST https://YOUR-WORKER.workers.dev/v1/orders \
  -H "Content-Type: application/json" \
  -H "Authorization: Bearer sk_test_abc123..." \
  -H "Idempotency-Key: unique-request-id-123" \
  -d '{"amountCents": 150000, "currency": "GYD", "description": "Order #1234"}'

Idempotency

Include an Idempotency-Key header on POST requests to prevent duplicate operations. Keys are valid for 24 hours. If you retry a request with the same key, you'll receive the original response.

Order Statuses

  • pending — Order created, awaiting payment
  • authorized — Card authorized, not yet captured
  • captured — Payment captured (funds transferred)
  • partially_captured — Partial capture
  • voided — Authorization voided
  • failed — Payment failed
  • refunded — Fully refunded
  • partially_refunded — Partial refund
  • disputed — Chargeback opened
  • chargeback_won — Dispute won
  • chargeback_lost — Dispute lost

Signature Verification

Webhooks include a signature header for verification: 

X-Neuereatec-Signature: t=1695729600,v1=5d2a9b...

To verify:

  1. Extract timestamp (t) and signature (v1) from header
  2. Check timestamp is within 5 minutes of current time
  3. Compute HMAC-SHA256 of {timestamp}.{body} using your webhook secret
  4. Compare computed signature to provided signature (constant-time)

Node.js Example

const crypto = require('crypto');

function verifyWebhook(body, signature, secret) {
  const [tPart, v1Part] = signature.split(',');
  const timestamp = tPart.split('=')[1];
  const providedSig = v1Part.split('=')[1];
  
  // Check timestamp within 5 minutes
  const age = Math.floor(Date.now() / 1000) - parseInt(timestamp);
  if (Math.abs(age) > 300) {
    return { valid: false, reason: 'timestamp_expired' };
  }
  
  // Compute expected signature
  const signedPayload = `${timestamp}.${body}`;
  const expected = crypto
    .createHmac('sha256', secret)
    .update(signedPayload)
    .digest('hex');
  
  // Constant-time comparison
  const valid = crypto.timingSafeEqual(
    Buffer.from(expected),
    Buffer.from(providedSig)
  );
  
  return { valid };
}

Retry Policy

Failed webhook deliveries are retried with exponential backoff: 1 min, 5 min, 15 min, 1 hour, 4 hours, 12 hours, 24 hours. Events are marked as exhausted after 8 failed attempts.

Go Live Checklist

Steps required to transition from sandbox to production.

  • Partner agreement with acquiring bank
  • Production MID and credentials
  • Replace mock processor with bank's hosted checkout/API
  • PCI DSS compliance validation
  • BoG PSP license (if operating as payment facilitator)
  • Production domain with SSL
  • Production Firebase project (if using Firestore mirror)
  • Monitoring and alerting configured
  • Incident response plan documented
