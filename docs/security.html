Security Overview

Payment Gateway Security Architecture

A summary of security measures implemented in Neuereatec Pay, designed for review by acquiring banks and compliance teams.

Executive Summary

Neuereatec Pay is a payment gateway designed with security as a foundational principle. The architecture ensures that sensitive card data (PAN, CVV, expiry) never touches merchant systems, minimizing PCI DSS scope for merchants using our hosted checkout.

Security ControlImplementation
Card Data Isolation Hosted checkout — card data never enters merchant application
API Authentication Per-merchant secret keys (HMAC-hashed at rest)
Webhook Security Timestamped HMAC-SHA256 signatures with replay protection
Transport Security TLS 1.3, HSTS, secure headers
Data at Rest Encrypted storage, no PAN/CVV persistence
Access Control Per-merchant data scoping, audit logging

Card Data Handling

What We Store

  • Transaction reference IDs
  • Order amounts and currency
  • Transaction status and timestamps
  • Merchant identifiers

What We NEVER Store

  • Primary Account Number (PAN) — card numbers never written to database
  • CVV/CVC — security codes never persisted
  • Full expiry date — not stored in transaction records
  • Cardholder name — not collected or stored

Hosted Checkout Flow

  1. Merchant creates an order via API (no card data)
  2. Customer is redirected to Neuereatec Pay hosted checkout
  3. Card details entered directly on our secure page
  4. Card data processed in-memory, never written to storage
  5. Result communicated via signed webhook

API Security

Authentication

  • Per-merchant API keys with test/live separation (sk_test_/sk_live_)
  • Keys hashed using HMAC-SHA256 before storage
  • Bearer token authentication on all API calls
  • Key rotation supported without service interruption

Request Protection

  • Rate limiting per IP and per merchant
  • Idempotency keys for POST requests (24-hour validity)
  • CORS allow-list configuration
  • Request body validation and sanitization

Webhook Security

  • HMAC-SHA256 signatures on all webhook payloads
  • Timestamp included in signature to prevent replay
  • 5-minute tolerance window for clock skew
  • Event ID deduplication for additional replay protection
  • Exponential backoff retry with up to 3-day delivery window

Infrastructure Security

Hosting

  • Cloudflare Workers — Edge deployment with built-in DDoS protection
  • D1 Database — Serverless SQL with automatic encryption
  • No persistent servers to patch or maintain
  • Automatic TLS certificate management

Security Headers

  • Content-Security-Policy — Restricts resource loading
  • Strict-Transport-Security — Enforces HTTPS
  • X-Frame-Options: DENY — Prevents clickjacking
  • X-Content-Type-Options: nosniff — Prevents MIME sniffing
  • Referrer-Policy: strict-origin-when-cross-origin
  • Cache-Control: no-store — Prevents sensitive data caching

Secrets Management

  • All secrets stored in Cloudflare Workers secrets (encrypted)
  • No secrets in source code or configuration files
  • Separate secrets for test and production environments
  • Fail-closed if required secrets are missing

Compliance Considerations

PCI DSS

The hosted checkout architecture is designed to reduce PCI DSS scope for merchants:

  • Merchants using hosted checkout typically qualify for SAQ A
  • Card data never transits merchant systems
  • Gateway infrastructure designed for PCI DSS service provider compliance

Data Protection

  • Data minimization — only necessary data collected
  • Encryption in transit and at rest
  • Audit logging for compliance and forensics
  • Designed for compliance with Guyana's Data Protection Act

AML/CFT

  • Merchant KYB data collection capabilities
  • Transaction monitoring and reporting infrastructure
  • Audit trail for regulatory examination

Audit and Logging

All sensitive operations are logged with:

  • Action type (order created, captured, refunded, etc.)
  • Actor identification (merchant ID, system)
  • Timestamp (ISO 8601 format)
  • IP address of requestor
  • Resource identifiers (no sensitive data)

Audit logs are:

  • Immutable (append-only)
  • Retained per regulatory requirements
  • Queryable by merchant for their own transactions

Incident Response

In the event of a security incident:

  1. Immediate containment and assessment
  2. Notification to affected parties within required timeframes
  3. Root cause analysis and remediation
  4. Post-incident review and documentation
